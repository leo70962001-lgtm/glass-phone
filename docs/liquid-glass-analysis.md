# Liquid Glass 分析與學習筆記

對象：Good Machines Lab 的 [Liquid glass](https://goodmachines.ai/lab/liquid-glass)，以及它引用的 [kube.io 折射文章](https://kube.io/blog/liquid-glass-css-svg/)。
分析日期：2026-11-04。方法：讀它的實作、用測試圖實測，再和我們 `a63dd16` 那一版用同一張桌布、同樣 375×812 @2x 對照。

> 頁面沒有授權聲明，它內部的 `implementation-notes.md` 也沒有公開（404）。這份筆記只記做法和參數，**不要複製它的程式碼**；要做就用這裡的原理自己寫。
> 對照圖放在 `refs/goodmachines/compare-v1.png`（不進公開 repo）。

> **狀態（2026-11-04）**：第 7 節的 0–5 都已做進主畫面，結果在第 8 節。

## 1. 結論

它和我們不是同一種玻璃：

| | Good Machines | 我們 |
|---|---|---|
| 模型 | 2D 距離場＋「一次折射」的表面公式 | 3D SDF 光線追蹤（折射、全反射、多次反彈） |
| 外觀目標 | 薄的 iOS 26 控制元件 | 厚的實體玻璃塊 |
| 形狀數 | 最多 8 個 | 約 25 個 |
| 圖案 | 畫在玻璃**上面**，會自動換深淺 | 埋在玻璃**裡面**，會被折射 |

它看起來像 iOS，不是因為算得比較精確（它其實更簡化），而是這四件事：

1. 折射集中在最外面約 3 px。
2. 真正的高斯模糊。
3. 整圈連續的細亮邊，沒有暗槽。
4. 依底下明暗自動切換玻璃與文字顏色。

上一版是只看貼文就做的，**「液態玻璃」預設其實還是厚玻璃**：下面的實測顯示，它最外圈的折射只有對方的約 1/5，幾乎沒有模糊。

括號內，對方是「折射 / 邊緣寬度」。\* 這個點落在編碼的折返處，讀數不可靠。對方量 62 pt 的圓，我們量 60 pt 的圖示；我們的玻璃有高度，所以把圖示單獨移到畫面正中央再量，避開透視位移（不在中央時，邊緣會偏約 2 pt）。

- **力道**：同樣叫液態玻璃，我們最外圈 2.5 pt，對方 12.9 pt，差約 5 倍。
- **曲線形狀**：對方是陡降曲線，一半以上的彎折在最外 3 pt；我們從邊緣起幾乎是平的，要到 5 pt 以後才明顯下降。這是「細透鏡邊」和「厚倒角」觀感的主要差別。
- 實測值和它的公式對得上（t=2 算出 7.9、量到 7.4；t=5 算出 3.3、量到 3.1）。

### 2.2 邊緣光（在純灰 #808080 = 128 上讀亮度，對方光源在左上、我們在右上）

| 位置 | 對方 Apple | 我們 參考圖 | 我們 液態玻璃 |
|---|---:|---:|---:|
| 朝光角，t=0.5 | 252 | 174 | 173 |
| 背光角，t=0.5 | 244 | 148 | 151 |
| 上下左右，t=0.5 | 223–226 | 150–170 | 145–172 |
| t=2 | 171–194 | 114–139 | 122–136 |
| t=5 | 146–150 | 105–136 | 118–147 |
| 朝光角內部亮斑 | 沒有 | 離邊 8 pt 有 246 | 離邊 6 pt 有 251 |
| 玻璃本體 | 143 | 約 147 | 約 146 |
| 玻璃外 t=-1 | 117–121 | 受光側 99–103，背光側 165–243（焦散） | 受光側 107–112，背光側 157 |

- 對方是**一整圈很亮的細線**：亮度單調降回本體，整圈最暗的地方也比本體亮很多；光源那角和正對面的角最亮。
- 我們的邊緣也是一整圈，但**亮度只有 150–175，緊接著是比本體更暗的暗槽（105–136），朝光角內還有一塊亮斑**，玻璃外又有焦散。這些正是「厚、實體感」的來源，也是不像 iOS 的原因。

### 2.3 其他實測

- 模糊：對方 Apple 預設 σ = 6 px。我們的 `uFrost` 走 mip：霧面 0.1 大約只有 0.8 級 LOD（由公式估算），約 1 px，所以內部幾乎是透明的。
- 融合：兩邊是同一條二次平滑聯集公式，只差 k。距離 gap 時要接起來，條件是 gap < k/2。對方 k = 融合距離，10 要靠到 5 px 才連；我們 k = 2 × 融合距離（`main.js:181`），10 就是 10 pt。分裂中的小泡它另外強制 k ≥ 26。
- 自動明暗：同一張桌布上，右上工具列在深藍處會切成暗玻璃＋白圖示，其他三塊是亮玻璃＋深色圖示。
- 效能（RTX 5060，375×812 @2x，同步讀回量測）：對方 0.3–0.4 ms；我們低畫質靜止 0.6、拖曳 1.1 ms。**這張顯卡太快，差距不能代表手機**，兩邊都沒有手機數據。
- 覆蓋面積：對方每幀畫滿 117 萬像素（它自己的計數），離玻璃 96 px 外才提早結束。我們只畫約 52 萬像素（計算值），但每個像素最壞約 100 次 3D SDF；對方約是 5 次距離場＋2 輪形狀迴圈。

## 3. 它怎麼做

### 3.1 管線
只有全螢幕一個玻璃 pass。圖片和控制元件的軌道先畫進場景快取，再建高斯金字塔，然後玻璃 pass 一次處理所有形狀。沒有逐形狀的繪製，所以沒有接縫問題，但形狀多了每個像素都要付成本，這是它上限 8 個的原因。

### 3.2 折射
- 高度剖面是凸的超橢圓：`h(x) = (1 - (1-x)^4)^(1/4)`，x 從邊緣 0 到邊緣寬度處 1。公開來源是 kube.io。
- 用距離場的梯度當朝外方向、剖面斜率當傾斜量，組成法線，讓垂直向下的光線以 IOR 1.5 折射一次，得到偏移方向，再乘上「折射」px。**相當於把厚度當成一個可調的倍率**，不追蹤光線。
- 唇邊：凸面和它的反相用平滑函數混合，越過頂點後斜率變負，中間會縮小。iOS 開關的滑塊就是這種形狀。
- 放大：往「融合後的中心」靠攏。
- 大玻璃折射更強：`clamp(sqrt(短邊 / 62), 0.75, 1.7)`，同時影響折射和邊緣寬度。
- 抗鋸齒：用折射後取樣座標的螢幕導數算 LOD，被擠壓的邊緣不會出現閃爍。
- 色散：三個通道沿同一偏移方向分別縮放 ±0.45×色散。

### 3.3 模糊
把高斯金字塔存進同一張貼圖的 mip：每級再做一次 σ≈1.3 的可分離模糊並減半，每級兩個小 pass。之後**任何模糊半徑都只要一次 `textureLod`**，比硬體盒狀 mip 乾淨很多，也比多點取樣便宜。σ 小於第 0 級時，改用銳利場景取 4 點再淡入。

### 3.4 融合
- 所有形狀依序做平滑聯集，得到一個場。
- **材質也融合**：每個形狀依 `exp(-(d - 最近d) / (6 + 融合距離))` 當權重，把中心、折射、模糊、色調、明暗全部混合。這樣融合交界不會有接縫，也不需要我們的「只畫離自己近的那一半」。
- **出生和消失不用縮放**：把距離場加上 `(1-存在度)×30`，形狀就從母體裡長出來、再沉回去，沒有跳動。我們現在是縮放，收合時還要切換隱藏。

### 3.5 表面（依序）
鮮豔度 → 霧面（亮玻璃混白、暗玻璃混石墨色，再往底色偏）→ 底色滲入（用 σ≈12 的模糊場）→ 染色（色調乘上背景亮度，保持透明感）→ 亮度 → 實心度（控制元件靜止時的白）。

### 3.6 光
- 邊緣：`exp(-距內側距離 / 邊緣光寬)` × 兩個瓣：`0.12 + 朝光^1.6 + 0.8 × 背光^1.6`。**兩個相對的瓣＋常數底**，就是整圈不斷的原因。
- 再加一層很淡的 Fresnel，鋪在彎曲的邊緣上。
- 光源角度 = 設定值＋手機傾斜＋拖曳速度造成的飄移（最多 ±18°），高光會跟著玻璃滑動。
- 陰影：對距離場偏移 5 px 取一次，柔和且只畫在玻璃外。比我們的 6 次掃掠便宜很多。

### 3.7 自動明暗
**不在著色器裡判斷**。
- CPU 存一張 160 px 的線性亮度小圖，算形狀範圍內的平均亮度。
- 遲滯：亮玻璃低於 0.14 才切暗，暗玻璃要到 0.22 才切回，不會在門檻附近閃。
- 只有短邊 ≤ 96 px 的小形狀會翻；面板固定亮色。這一條來自 Apple 的方向。
- 玻璃用慢彈簧，文字用快很多的彈簧（約 0.2 秒），切換中對比不會掉。
- 文字深淺另外算：依「實際看得到的亮度」判斷。影片桌布每 500 ms 更新一次。
- 明亮圖片的壓暗：只在玻璃周圍 90 px 內，強度依整張圖平均亮度決定（Apple 建議 35%）。

### 3.8 動態
所有值都是阻尼彈簧，固定 120 Hz 步進，動完才停止重畫。對方選的（k, c）：

| 用途 | k | c | 感覺 |
|---|---:|---:|---|
| 移動 | 320 | 24 | 一次柔和過衝 |
| 按壓膨脹 | 420 | 17 | 彈一下 |
| 速度拉伸 | 380 | 22 | |
| 型變 | 230 | 25 | 幾乎不過衝，位置和尺寸共用 → 釘住的角不會動 |
| 分裂 | 110 | 17 | 故意比型變慢，才看得到融合 |
| 明暗 | 120 | 22 | |
| 文字深淺 | 700 | 53 | 約 0.2 秒 |
| 實心↔玻璃 | 260 | 32 | 約 0.3 秒 |

`prefers-reduced-motion` 時，全部改成臨界阻尼，自動動態也會停掉。

### 3.9 型變（Morph）
**沒有特殊演算法，只是目標值換掉，由彈簧帶過去。**
- ⋯ 膠囊 64×44 → 面板 220×高（列 44 px），靠右上角釘住；舊內容 0.15 秒淡出、新內容 0.4 秒淡入。
- 「＋ New」膠囊 150×56 → 三顆 56 的圓。旁邊兩顆平常是 8×8 藏在裡面、存在度 0。

### 3.10 iOS 控制元件
- 比例：開關軌道 64×28、滑塊 38×24，略放大讓透鏡看得到。
- **軌道畫進場景**（最多 6 個圓角矩形），滑塊的透鏡才折射得到軌道。
- 滑塊靜止時是實心白（開關與滑桿 0.92、分段 0.55），按下變透明玻璃並膨脹 1.4 倍，移動時拉伸到最多 1.42 倍。
- 滑塊材質獨立：模糊 ≤ 1、霧面 ≤ 0.04、折射 ≥ 24；開關與滑桿用唇邊，分段用凸面。
- 被點選而移動時，滑塊也會先變成透鏡，抵達後才變回實心。

### 3.11 穩定性
- 自動降解析度：先在閒置幀量出螢幕真正的更新率，再判斷慢不慢，所以 30 Hz 的省電模式不會被誤判成 GPU 太慢。可以升回去，有防來回機制；靜止幀永遠全解析度；只縮玻璃 pass。
- 影片：有 `requestVideoFrameCallback`，但回呼停止時也會輪詢 `currentTime`（WebKit 會卡住）。
- 文字：每個標籤各自光柵化成小貼圖，畫成四邊形；深色字略細、淺色字略粗。
- 沒有 WebGL2 時退回 CSS `backdrop-filter`。透明的真實控制元件覆蓋在玻璃上，供鍵盤和螢幕閱讀器使用。
- 手機傾斜會依螢幕方向校正。
- 錄影：`captureStream` + `MediaRecorder`，優先 H.264 MP4，退回 WebM，14 Mbps。
- 連結分享：`#s=` base64url JSON，讀取時逐項驗型別。

## 6. 對照後發現我們自己的問題

都是從程式碼推得，還沒在實機驗證。

1. **省電模式會被誤判（`main.js:874-875`）**：幀時間 > 25 ms 就算慢。iPhone 低電量模式把 rAF 壓到 30 Hz，影片桌布又讓畫面一直重畫，幾秒內解析度就會一路降到 1 倍，而且**永遠不會升回來**。每次降級還要重建整個版面。
2. **iPhone 影片桌布可能卡住（`main.js:260-262`）**：有 `requestVideoFrameCallback` 就只靠它，沒有輪詢備援。
3. **橫向握持時陀螺儀方向錯誤（`main.js:396-411`）**：沒有依 `screen.orientation` 校正。
4. **文字層成本高（`main.js:154-161`）**：每次都重畫並上傳整張全螢幕畫布；動畫時 30 Hz，對手機不便宜。
5. **`prefers-reduced-motion` 只影響桌布動畫（`main.js:27`）**，果凍、抖動、視差都不受影響。
6. **融合距離的數字比標示的大一倍（`main.js:181`）**：不算錯誤，但數值不能和對方直接比較。

## 7. 建議的做法

**保留 3D 模式，另外新增「透鏡模式」**，兩者用預設切換。不要改成對方的單一全螢幕 pass：25 個形狀逐像素跑不動，要維持逐塊繪製＋鄰居清單，只把每塊的著色換成 2D 透鏡。融合交界改用它的距離權重混合材質。

| 順序 | 內容 | 工作量 |
|---|---|---|
| 0 | 修第 6 節的 1–3、5（風險小、直接影響手機） | 小 |
| 1 | 高斯金字塔＋透鏡著色器（折射曲線、模糊、整圈邊緣光、霧面、鮮豔、底色）＋六個對應預設 | 中 |
| 2 | 自動明暗（CPU 亮度小圖＋遲滯＋雙彈簧）；圖案改畫在玻璃上 | 中 |
| 3 | 全部改成阻尼彈簧；用「存在度」做出生和消失；⋯ 型變成面板＋玻璃上的文字 | 中 |
| 4 | iOS 控制元件（軌道畫進螢幕層），接到真實設定 | 中 |
| 5 | 拖放／貼上桌布、存 PNG、錄影、連結分享 | 小 |

參考圖比對、復原、逐形狀材質是調校工具，主畫面不太需要，先不做。

**做的時候學到的**
- 融合半徑不能一律放大：隔壁玻璃距離小於半徑時，平滑聯集會把輪廓拉鼓。改成靜止用小半徑、拖曳中的那一塊才加大。
- three r180 可以直接畫進 mip：`rt.texture.mipmaps` 配滿整條、`rt.viewport` 設該級尺寸、`setRenderTarget(rt, 0, level)`。讀寫要分兩張貼圖，否則是回授迴路。
- 合成要在 sRGB 空間做：霧面、邊緣光的比例是用眼睛看到的亮度定的，在線性空間相加會偏暗。陰影和壓暗也一樣。
- 放在托盤上的圖示不能投影到桌布：沒有模糊的預設會把陰影折射成色塊。
- `readRenderTargetPixelsAsync` 等待期間 `PIXEL_PACK_BUFFER` 還綁著，這時直接呼叫 `readPixels` 會失敗（只影響測試程式）。

**沒有做的**：捲動桌布、自動滑行、參考圖比對、復原、逐形狀材質、加形狀、沒有 WebGL2 時的退路、給鍵盤和螢幕閱讀器的控制元件。

**還沒驗證**：真實手機上的流暢度、陀螺儀、低電量模式、iPhone 上的影片備援、分享存檔、錄影。都只在這台電腦的手機尺寸模擬（RTX 5060）測過；這裡一幀 1–2.3 ms，不能代表手機。
